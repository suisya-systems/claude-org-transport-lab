# AC-1 状態 2: IME 変換中ナッジ注入の手動テスト手順書

設計 SoT: [`docs/design/renga-decoupling.md`](../docs/design/renga-decoupling.md) §7.1 AC-1 状態 2。

## なぜこの状態だけ手動か（自動化しない根拠）

自動判定 (run_ac1.py) は `wezterm cli get-text` による画面観測ヒューリスティックで
受信側状態を分類している。しかし **get-text が観測できるのは PTY 内の文字 grid のみ**である。
IME（日本語入力）の変換窓・候補リスト UI は **OS（IME フレームワーク）側のオーバーレイ**として
端末の grid の外に描画されるため、

- 「変換中である」ことを get-text から検知できない（broker の静止確認は入力欄の
  確定済み文字しか見えない）
- 「変換窓・候補 UI が壊れた」ことも get-text から検証できない

の両面で自動化が成立しない。よって状態 2 のみ人間参加の手動テストとする
（事前 codex design review 確定事項 (5)）。

**この制約は本番設計にも残る既知リスクである**: broker の静止確認 (§4.3) は
「未確定の IME 変換中」を idle と誤認してナッジを打鍵しうる。本テストは
その誤認時に何が起きるかを実測するものであり、AC-1 の合否（計画中止の
足切り）を決める。

## 事前準備

実施者: 窓口 + ユーザー（日本語 IME を使う人間）。所要時間: 約 10 分。

1. リポジトリの `spike/` ディレクトリで broker をテストモード起動する:

   ```powershell
   cd <repo>/spike
   py -3 manual_ime_session.py
   ```

   スクリプトが行うこと:
   - broker 起動 + 検証用 Claude TUI を**新規 WezTerm ウィンドウ**に spawn
     （folder trust prompt は自動承認される）
   - `idle 確認後、Enter キーで 5 秒後にナッジ配達` の対話ループを提供
     （observer → claude-spike 宛にメッセージを enqueue し、ナッジ配達が走る）
2. spawn された WezTerm ウィンドウをフォーカスし、日本語 IME (Microsoft IME 等) を
   有効にしておく。

## テスト手順（4 ケース）

各ケースで: コンソール側で Enter を押す → **5 秒以内に** WezTerm 側で指定の
IME 状態を作り、そのまま維持する。ナッジは入力欄静止が確認されるまで defer される
（2 秒間隔で再試行、最大 60 秒）。

### ケース A: 変換窓を開いたまま維持（未確定文字列あり）

1. Claude の入力欄に「きょうのてんき」と入力し、**スペースキーで変換候補を表示したまま**待つ。
2. ナッジ配達タイミング（コンソールのログで `nudge_deferred` / `nudge_sent` が見える）を跨いで
   10 秒以上維持する。
3. 観察ポイント:
   - 変換窓・候補リストが消えたり崩れたりしないか
   - 未確定文字列（下線付きの「きょうのてんき」）が破壊・確定・消失しないか
   - ナッジ文字列が未確定文字列に混入しないか
4. その後変換を確定（Enter）し、入力欄の文字を Ctrl+C でクリアする。
5. クリア後（入力欄静止後）にナッジ 1 行が配達・送信されることを確認する。

### ケース B: 変換確定の瞬間とナッジが競合する

1. コンソール側 Enter の直後に「にほんごにゅうりょく」と入力し、変換 → 確定を
   **2〜3 秒間隔で繰り返す**（確定とナッジ打鍵の競合を狙う）。
2. 観察ポイント:
   - 確定済み文字列が欠落・重複しないか
   - ナッジ文字列が入力途中の行に混ざらないか（defer が効いていれば混ざらない）

### ケース C: 未確定のまま放置 → broker が idle と誤認するか

1. 「てすと」と入力し**未確定（下線付き）のまま**何もしない。
2. broker は get-text で未確定文字を観測できる場合（端末 inline 描画）と
   できない場合（IME ウィンドウ描画）がある。コンソールログで
   `nudge_deferred (state=input_pending)` になるか `nudge_sent` まで進むかを記録する。
3. `nudge_sent` まで進んだ場合（= idle 誤認）:
   - 未確定文字列がどうなったか（確定された / 消えた / ナッジと連結された）
   - 入力欄とナッジ行の最終状態
   を必ず記録する。**ここが本テストの核心**。

### ケース D: 対照群（IME オフ）

1. IME を無効（英数直接入力）にして入力欄を空にし、ナッジ配達を 1 回観察する。
2. ケース A〜C で乱れがあった場合に IME 起因かどうかを切り分ける基準にする。

## 合否基準（設計書 §7.1 AC-1 状態 2）

| 判定 | 条件 |
|---|---|
| **合格** | 全ケースで: 変換中の文字列・変換窓・確定操作が破壊されない。ナッジは defer され、変換確定（入力欄静止）後に配達される。ケース C で idle 誤認が起きても、未確定文字列が破壊されず、ナッジ行と分離されていれば合格（誤認 = 即不合格ではない。「窓口入力を壊す」かどうかが基準） |
| **不合格** | いずれかのケースで: 未確定文字列の消失・意図しない確定・ナッジ文字列の混入・未送信テキストの勝手送信、が**再現可能に**発生する |
| 不合格時 | §4.3 の緩和策（defer 間隔・静止判定の強化等）を検討し、それでも解消しなければ **AC-1 足切り条項により計画ごと中止（棚上げ）**。勝手に基準を緩めない |

## 結果の記録

- 合否判定と根拠
